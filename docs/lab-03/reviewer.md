### 3. สิ่งที่ได้เรียนรู้จากการไป Review เพื่อน (Giving Feedback)

- **การตรวจจับ Concurrency Bug ในการสร้าง Ticket Number:** ใน PR #49 ตรวจพบว่าการใช้ `count` ของตารางเพื่อนำมาสร้างหมายเลขตั๋วถัดไป เสี่ยงต่อการเกิด race condition และ duplicate key error (`P2002`) เมื่อมี request เข้ามาพร้อมกัน การเสนอแนะให้เปลี่ยนไปใช้การดึงค่าลำดับสูงสุดจริง (`getHighestTicketSequence()`) ช่วยเพิ่มความเสถียรและความทนทาน (Resilience) ให้กับระบบ
- **การบังคับใช้ Safety Guards เชิงลึกในระดับ Backend และ UI:** ใน PR #48 (Admin User Management) ได้ร่วมตรวจสอบการทำงานของกฎความปลอดภัย BR-32 และ BR-33 (การห้าม Deactivate ตนเอง และการห้ามลดบทบาท/ปิดการใช้งาน Admin คนสุดท้าย) ซึ่งพบว่าการป้องกันต้องทำอย่างรัดกุมทั้งสองฝั่ง คือมี disabled state + tooltip ใน UI และมี HTTP 403 status พร้อม error code เฉพาะในระดับ API
- **การป้องกันข้อมูลรั่วไหล (Zero Data Leakage):** ใน PR #47 ได้ตรวจสอบการแยกสิทธิ์ระหว่าง Public Comments และ Internal Notes โดยยืนยันว่า Request จากฝั่ง Requester ที่พยายามเข้าถึง Internal Notes จะต้องถูกบล็อกด้วย 403 Forbidden ทันที และไม่ส่งทั้งเนื้อหาหรือแม้กระทั่งจำนวนนับ (count) กลับไป เพื่อรักษาความปลอดภัยของข้อมูลภายในทีม IT Staff
- **การรักษามาตรฐานด้วยการร้องขอการแก้ไข (Requested Changes):** ใน PR #50 (End-to-End Tests) ได้ตรวจสอบพบว่าระบบยังขาดการรองรับ query parameter `isActive` ใน Endpoint `GET /api/admin/users` และขาด status dropdown filter ในหน้า UI ตามที่ระบุในข้อกำหนด จึงได้ส่งผลการรีวิวเป็น Requested Changes เพื่อให้เพื่อนทำการเติมเต็มฟังก์ชันและอัปเดตเอกสารให้ครบถ้วน 100% ก่อนที่จะ Approve และ Merge สู่ Staging

### 4. ประโยชน์ต่อคุณภาพของระบบและความพร้อมในการส่งมอบ (Quality & Delivery Impact)

- **บรรลุมาตรฐาน 100% Green Test Suite & Zero Regression:** จากการรีวิวและร่วมกันตรวจสอบอย่างละเอียด ทำให้ระบบ TokTickIT ใน Lab 03 ผ่านการทดสอบทั้งหมดโดยไม่มีข้อผิดพลาด (Server: 211/211 tests, Client: 86/86 tests, Spec Invariants: 44/44 ผ่านฉลุย) และ E2E Playwright Tests ผ่านครบทุก User Journeys ทั้ง 3 Viewports (Desktop, Tablet, Mobile)
- **ลดหนี้ทางเทคนิค (Technical Debt):** ข้อสังเกตและคำแนะนำระหว่างการรีวิวช่วยกำจัดโค้ดที่ซ้ำซ้อน จัดการ error handling ให้เป็นระบบ และกำจัดปัญหา responsive overflow ตั้งแต่เนิ่นๆ ทำให้โค้ดมีความเป็นระเบียบ อ่านง่าย และง่ายต่อการต่อยอดในอนาคต
- **สร้างวัฒนธรรมความร่วมมือแบบมืออาชีพ (Collaborative Engineering Culture):** กระบวนการ Peer Review ได้พิสูจน์แล้วว่าเป็นกลไกที่มีคุณค่าอย่างยิ่งในการถ่ายทอดความรู้ระหว่างผู้พัฒนา การเปิดรับฟังข้อเสนอแนะอย่างสร้างสรรค์ และการช่วยกันอุดช่องโหว่ของระบบ ส่งผลให้ผลงานที่ส่งมอบมีเสถียรภาพ ความปลอดภัย และตรงตามความต้องการทางธุรกิจอย่างแท้จริง
