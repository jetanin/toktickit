# Lab 2 Sprint Engineering Specification

## 1. Sprint Goal

Build the Requester-facing IT support ticketing MVP with a reusable UI foundation (Zen Green theme), enabling Requesters to create tickets with attachments, view their paginated ticket list, and manage ticket details. This sprint uses a temporary Development Requester selector to simulate multi-user ownership before real authentication is introduced.

## 2. Stakeholder Request Interpretation

The IT department needs a professional, responsive portal for end users (Requesters) to submit and track support tickets. Requesters must be able to fill out ticket details, upload up to 5 attachments, and view their submitted tickets in a searchable, filterable list. They can also view ticket details and manage their attachments (including soft removal). Since authentication is not yet implemented, a temporary "Development Requester" selection screen will be used to switch between test users and enforce ownership (users can only see their own tickets).

## 3. Scope

### Included

- Development Requester selection screen and context switching.
- Create Ticket workflow with frontend/backend validation.
- My Tickets workflow (paginated list, search, filter, sort).
- Requester Ticket Detail screen (read-only ticket data).
- Attachment lifecycle (upload, download, soft removal).
- Zen Green UI specification (components, responsive layouts, empty/loading/error states).
- Database changes for Tickets, Attachments, Categories, Related Systems, and Requesters.

### Excluded

- Real authentication, login, logout, passwords, sessions, or real role-based authorization.
- IT Staff workflow (dashboard, queue, claiming, changing IT priority).
- Ticket collaboration (Public Comments, Internal Notes, Actions Taken).
- Ticket lifecycle status changes beyond the initial "New" status.
- Administrator management functions.

## 4. Functional Requirements

- **FR-01**: The system shall provide a Development Requester Selection screen to simulate user context.
- **FR-02**: The system shall allow the selected Requester to create an IT support ticket.
- **FR-03**: The system shall generate and display a unique official Ticket Number upon successful ticket creation.
- **FR-04**: The system shall allow the selected Requester to upload up to 5 attachments per ticket (JPG/JPEG, PNG, WEBP, PDF, max 5MB each).
- **FR-05**: The system shall display a paginated list of the selected Requester's tickets in "My Tickets", supporting search, filtering, and sorting.
- **FR-06**: The system shall restrict ticket visibility so a Requester can only view tickets they own.
- **FR-07**: The system shall provide a Ticket Detail screen showing read-only ticket information.
- **FR-08**: The system shall allow the selected Requester to soft-remove their own attachments by providing a confirmation and reason.
- **FR-09**: The system shall prevent downloading or previewing of soft-removed attachments.

## 5. Business Rules

- **BR-01**: The official Ticket Number is generated by the backend and must be unique.
- **BR-02**: A new Ticket begins with Current Status `New`. There should be no default values for `Requested Priority` or `Category` when creating a ticket.
- **BR-03**: Lab 2 uses a Development Requester selector instead of login. The selected identity is for testing only, is not authentication, and must be persisted in `localStorage`.
- **BR-04**: Inactive Requesters must not appear in the Development Requester selector.
- **BR-05**: Ticket Summary is required (max 100 characters) and Description is required (max 1000 characters).
- **BR-06**: Only JPG, JPEG, PNG, WEBP, and PDF files are permitted for attachments.
- **BR-07**: A single attachment cannot exceed 5 MB in size.
- **BR-08**: A ticket can have a maximum of 5 active attachments.
- **BR-09**: Removed attachments are soft-removed; their metadata remains visible but files cannot be downloaded.
- **BR-10**: Attempting to access a Ticket or Attachment belonging to another Requester must result in an ownership failure/unauthorized error.
- **BR-11**: The system shall prevent duplicate ticket submission. The Submit button must be disabled and show a busy state ("Submitting...") after the first click. If the API returns an error, the form must retain all user-entered data so the user can correct and re-submit without re-entering.
- **BR-12**: Uploaded attachment filenames must be sanitized before storage to prevent path traversal and special character issues. Storage filenames must be unique (e.g., UUID-based). The original filename is preserved in metadata for display purposes only.
- **BR-13**: If an attachment upload fails after the parent ticket was successfully created, the ticket remains valid and persisted. The user is shown an error message for the failed attachment and may retry the upload without re-creating the ticket.

## 6. UI Specification Summary

- **Theme**: Zen Green (#006B3C primary, #0B7A46 secondary, #EAF6EF pale green).
- **Application Shell**: Includes TokTickIT title, active Development Requester identity display, navigation (My Tickets, Create Ticket), and responsive mobile nav.
- **Create Ticket**: Responsive multi-column layout on desktop, stacking vertically on mobile. Required fields marked with red asterisks. Validation messages appear near associated fields.
- **My Tickets**: List/table of tickets.
  - **Search**: By Ticket Number, Summary, and Requester.
  - **Filter**: By Category, Requested Priority, and Status.
  - **Sort**: By Ticket Number, Created Date, and Last Update (default DESC).
  - **Pagination**: Default 8 items per page.
  - Includes clear empty state (no tickets) and no-results state (search mismatch).
- **Ticket Detail**: Read-only layout distinguishing ticket info from attachment actions.
- **Attachments**: Display active, uploading, invalid, and removed states. Soft removal requires selecting a reason from a dropdown, with the last option being "อื่นๆ (โปรดระบุ)" for free-text input.
- **Responsiveness**: Desktop (>= 992px), Tablet (768-991px), Mobile (< 768px).

## 7. Data Changes

- **DevelopmentRequester**: id, name, email, isActive.
- **Ticket**: id, ticketNumber (unique), requesterId, categoryId, relatedSystemId, summary, description, requestedPriority, itPriority, currentStatus, createdAt, updatedAt.
- **Attachment**: id, ticketId, originalFilename, storagePath, size, mimeType, removalReason, removedAt.
- **Category**: id, name, isActive.
- **RelatedSystem**: id, name, isActive.

### 7.1 Index and Constraint Decisions

| Column / Constraint          | Type                             | Justification                                                                                                                                                     |
| ---------------------------- | -------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Ticket.ticketNumber`        | UNIQUE constraint + B-tree index | Business key used for search (My Tickets search bar) and display. Must be unique to prevent duplicate official numbers. Index accelerates `LIKE 'TKT-%'` lookups. |
| `Ticket.requesterId`         | B-tree index                     | Every `GET /api/tickets` query filters by `requesterId` (ownership). Without an index, full table scans would degrade as ticket volume grows.                     |
| `Attachment.ticketId`        | B-tree index                     | Ticket detail always joins/fetches attachments by `ticketId`. Index avoids sequential scan on the Attachment table.                                               |
| `DevelopmentRequester.email` | UNIQUE constraint                | Email is a natural key for requesters. Prevents duplicate requester records during seeding and future user management.                                            |

### 7.2 Seed Data Requirements

Minimum seed data for development and testing:

| Entity                          | Minimum Count | Notes                                                                             |
| ------------------------------- | ------------- | --------------------------------------------------------------------------------- |
| DevelopmentRequester (active)   | ≥ 4           | Enough to test ownership filtering and requester switching                        |

## 8. API Contract

- `GET /api/dev-requesters`: Retrieve active Development Requesters.
- `GET /api/categories`: Retrieve active Categories.
- `GET /api/related-systems`: Retrieve active Related Systems.
- `POST /api/tickets`: Create a new Ticket.
- `GET /api/tickets`: Retrieve a paginated, searchable, filterable list of tickets owned by the selected Requester.
- `GET /api/tickets/:id`: Retrieve details of a specific ticket owned by the selected Requester.
- `POST /api/tickets/:id/attachments`: Upload an attachment.
- `GET /api/attachments/:id`: Retrieve attachment metadata (not the file content itself).
- `GET /api/attachments/:id/download`: Download an active attachment.
- `PATCH /api/attachments/:id/remove`: Soft-remove an attachment (requires reason payload).

## 9. Acceptance Criteria

- **AC-01** Given valid Ticket data, when the Requester submits the form, then one Ticket is saved and the official Ticket Number is displayed.
- **AC-02** Given no Development Requester is selected, when the user attempts to open My Tickets, then the Requester Selection screen is shown.
- **AC-03** Given Requester B is selected, when a Ticket belonging to Requester A is requested, then the Ticket data is not returned (HTTP 403 or 404).
- **AC-04** Given a user is on the Requester Selection screen, when it loads, then only active Requesters are shown in the options.
- **AC-05** Given a file larger than 5MB, when the user attempts to attach it, then the frontend prevents upload and shows an error message.
- **AC-06** Given a Requester has 0 tickets, when they view My Tickets, then an empty state illustration/message is displayed.
- **AC-07** Given an active attachment on a Ticket, when the user soft-removes it and provides a reason, then the attachment is marked as removed and can no longer be downloaded.
- **AC-08** Given a paginated ticket list, when the user clicks next page, then the appropriate next subset of tickets is loaded and displayed.
- **AC-09** Given a Requester is on the selection screen, when they select a different Requester, then the identity context switches, localStorage is updated, and My Tickets shows only the newly selected Requester's tickets.
- **AC-10** Given a Requester is on any screen, when the viewport is resized to mobile (<768px), then all content remains accessible without horizontal scrolling and the ticket table converts to a card layout.
- **AC-11** Given the API returns a 500 error or is unreachable, when the user is on any screen, then a user-friendly error message is displayed and any form data the user has entered is preserved.

## 10. Definition of Done

- All approved scope implemented and Acceptance Criteria satisfied.
- Unit, API, UI, and E2E tests are planned, written, and pass.
- Conformance to Zen Green UI, responsive specifications, and API contracts.
- Success, failure, empty, and ownership boundary cases handled correctly.
- Required branches, PR workflow, and peer reviews completed.
- PDF evidence submitted.

## 11. Assumptions and Decisions

- **Storage**: `localStorage` is used to persist the selected Development Requester context across page reloads.
- **Pagination**: The default page size for ticket lists is 8 items.
- **Removal Reason**: Attachment soft-removal enforces selecting a predefined reason, but provides an "อื่นๆ (โปรดระบุ)" (Other) option for custom reasons.
